# Railzway Docs

The self-hosted documentation site for Railzway, built with Next.js, Fumadocs,
MDX, and the canonical API contracts from `railzwayapis`.

## Development

```bash
pnpm install
pnpm api:generate
pnpm dev
```

`pnpm api:generate` reads the OpenAPI v2 files generated by Buf in the sibling
`railzwayapis` repository, copies them into `openapi/`, and regenerates the MDX
reference pages. Run `buf generate` there first whenever the public contract
changes. The copied specifications keep CI and container builds self-contained.

## Checks

```bash
pnpm lint
pnpm types:check
pnpm build
```

## API reference synchronization

After `railzwayapis/main` passes Buf CI, it sends an `api-spec-updated`
repository dispatch containing the exact API commit SHA. The
`Sync API reference` workflow checks out both repositories, runs `make generate`
and `pnpm api:generate`, verifies the documentation, and opens a pull request
containing only the generated OpenAPI specifications and reference pages.

Repository setup:

1. Create `railzwaylabs/railzway-docs` and enable GitHub Actions.
2. Add `DOCS_DISPATCH_TOKEN` to `railzwayapis`. Use a fine-grained token or
   GitHub App token that can send repository dispatch events to
   `railzwaylabs/railzway-docs`.
3. Add `DOCS_PR_TOKEN` to `railzway-docs` with permission to push branches and
   create pull requests. A GitHub App installation token is preferred. Using a
   token other than the workflow's built-in `GITHUB_TOKEN` ensures the generated
   pull request triggers `Docs CI`.
4. Allow GitHub Actions in `railzway-docs` to create pull requests as a fallback.
5. If `railzwayapis` is private, add `API_READ_TOKEN` to `railzway-docs` with
   read-only access to that repository.
6. Add `BUF_TOKEN` to `railzway-docs` if generation needs authenticated BSR
   access.

The docs workflow can also be started manually with a branch, tag, or commit
through `workflow_dispatch`.
